# Эксплуатация и первый выпуск исправлений

## Хранилища и конфигурация

Конфигурация приложения и maintenance-команд разрешается одинаково: `config.json` в каталоге
проекта или `HILLEYE_CONFIG_PATH`, затем переопределения `HILLEYE_*`. У CLI также есть явный
`--config`, который указывается перед подкомандой. Секреты можно задать в защищённом
`/etc/hilleye/hilleye.env`; unit читает его как необязательный EnvironmentFile.

Комплектный unit хранит `tracker.db`, `logs.db`, `uploaded_logs/` и `map_cache/` в
`/var/lib/hilleye`. Приложение проверяет запись в эти каталоги при старте. Файлы БД и OS locks
должны находиться на локальной файловой системе, общей для всех workers. Lock-файлы нельзя
удалять, пока работает хотя бы один процесс. Права на состояние выдаются пользователю `hilleye`.

## Backup, проверка и восстановление

Команды запускаются из каталога проекта с теми же конфигурацией и env overrides, что у сервиса:

```bash
/opt/Hilleye/venv/bin/python -m core.maintenance --config /opt/Hilleye/config.json backup --destination /var/lib/hilleye/backups
/opt/Hilleye/venv/bin/python -m core.maintenance verify /var/lib/hilleye/backups/hilleye-EXAMPLE.tar.gz
/opt/Hilleye/venv/bin/python -m core.maintenance restore /var/lib/hilleye/backups/hilleye-EXAMPLE.tar.gz --destination /var/lib/hilleye/restored
```

`bash backup.sh` — обёртка над backup. Для выбора Python: `HILLEYE_PYTHON=/opt/Hilleye/venv/bin/python`.
Каталог backup по умолчанию — `backups` рядом с tracker DB; `HILLEYE_BACKUP_DIR` его заменяет.

В архив входят обе БД, оригиналы upload с `.hilleye_meta.json`, настроенный каталог дисковых
логов и manifest с SHA-256. Кэш карт и конфигурационные секреты не входят. Backup требует
доступности настроенных источников и файлов, на которые ссылаются сохранённые раунды.
Недоступный источник приводит к ошибке backup, а не публикации неполного архива.

SQLite копируется через backup API, включая committed WAL. Публикация/удаление upload и
индексация координируются общими locks. Внешний игровой сервер может продолжать писать:
для каждого его файла сохраняется префикс размера, зафиксированного при открытии. Это не
единый момент времени для всех внешних файлов; после восстановления индекс пересобирается.

Готовый архив проверяется до атомарной публикации, имеет закрытые права и хранится локально
семь суток. Очистка старых архивов выполняется только после успешного нового backup. Названия
архивов содержат UTC. Расписание и копирование проверенного архива на другой носитель/сервер
настраиваются администратором; одно локальное хранилище не защищает от потери диска.

Restore отказывается писать в непустой каталог. Сначала проверяет архив, восстанавливает
файлы в staging, проверяет SQLite и переназначает пути раундов. Только затем публикует каталог.
В `restore-config.json` лежат нужные env overrides без секретов. Примените их к сервису и
выдайте его пользователю права на восстановленный каталог. Для backup/restore до первой
миграции поддерживается прежняя схема logs DB.

## Первое обновление и откат

1. Сохранить точную предыдущую версию кода, lock/requirements, конфигурацию, секреты и unit.
   Зафиксировать реальные текущие пути БД и логов; старый unit мог хранить logs DB в кодовом каталоге.
2. Остановить **все** workers Hilleye. Исходные файлы и WAL/SHM вручную не удалять.
3. Разместить новый код, но не запускать приложение. Его maintenance-командой создать и
   проверить backup старых данных, используя **старые реальные пути**, а не будущие defaults.
   Команда backup не мигрирует исходную схему.
4. Если пути меняются, восстановить архив в новый пустой подкаталог `/var/lib/hilleye`, например
   `/var/lib/hilleye/restored`. Применить storage overrides из `restore-config.json` через env file,
   включая `HILLEYE_LOGS_DIR`, если восстанавливались дисковые логи. Выдать владельца `hilleye:hilleye`.
5. Установить зависимости `uv sync --locked` или `pip install --require-hashes -r requirements.txt`
   в предназначенное сервису окружение. Обновить unit, выполнить `systemctl daemon-reload` и старт.
6. Проверить `/live`, `/ready`, открытие и скачивание сохранённого раунда, глобальный поиск,
   фоновые refresh/reindex и карту. Во время первой пересборки старое поколение индекса доступно.
   Проверить состояния источников и задания; успешный HTTP refresh может содержать `errors > 0`.

Миграции добавочные и транзакционные. Смешанные старые/новые writers не поддерживаются:
старый индексатор не понимает поколения. Для отката остановить все процессы, вернуть старый
код/окружение/unit и восстановить соответствующий pre-upgrade backup в пустое состояние.
Не запускать старый код на частично обновлённых данных. Сохранить новые данные отдельно,
если после обновления уже появились важные загрузки.

## Индексация и фоновые задачи

Настройки в `logs`:

| Поле | По умолчанию | Назначение |
| --- | ---: | --- |
| `periodic_scan` | `true` | Периодическое обнаружение и обновление |
| `scan_interval_seconds` | `60` | Интервал между запросами сканирования |
| `auto_scan_on_startup` | `true` | Немедленный первый проход |
| `regex_timeout_seconds` | `5` | Время regex-задачи в отдельном процессе |

Гарантия интервала означает частоту запуска при свободном владельце, а не срок завершения
любой большой переиндексации. Ошибки источника сохраняют прежние данные; исчезновение
раунда подтверждается двумя успешными сканированиями с промежутком не меньше минуты.
Неполная последняя строка дискового лога попадает в поиск после перевода строки или
пяти минут без изменений файла. Если запись затем продолжится с той же строки,
индекс строит новое поколение. Upload считается статическим и допускает последнюю
строку без перевода. Для изменившегося файла скан сверяет
SHA-256 обработанного префикса. Допись с совпавшим префиксом продолжает существующее
поколение, изменение старых строк строит новое. Скан неизменившегося файла использует его
идентификатор, размер и время изменения. При замене файла с принудительным сохранением
метаданных используйте reindex.

Задания имеют состояния `queued`, `running`, `succeeded`, `partial`, `failed`, heartbeat, прогресс и результат.
Статус `partial` означает ошибки отдельных источников или раундов. Выбранный в форме reindex
режим DEBUG сохраняется в БД и используется последующими сканами и импортами.
Refresh объединяются, очередь ограничена 32 ожидающими заданиями. Владельцы индексации и
карт выбираются раздельными OS locks. После аварии новый владелец подхватывает задания;
индекс продолжает с committed checkpoint, карта собирается заново в своём staging.
Полный reindex сохраняет список опубликованных раундов в той же транзакции, что и
их поколение. После перезапуска он повторно проверяет исходники и пропускает уже
опубликованные неизменившиеся раунды.

- `POST /logs/refresh`, `/logs/reindex`: ожидание до 25 секунд. При `background=1` или по
  истечении ожидания возвращается `202 {"ok": true, "job_id": "..."}`. Авторизация и CSRF сохраняются.
- Фоновый rebuild карты сохраняет прежние поля и добавляет `job_id`.
- `GET /api/v1/logs/jobs/{id}`: собственные задания пользователя, любые для администратора;
  чужой/неизвестный ID возвращает 404. Участники объединённого refresh видят общий результат.
- `GET /api/v1/logs/status`: свежесть источников, ошибки и необработанные байты. Сведения
  о чужих запущенных заданиях viewer не получает. Общий флаг `busy` доступен всем ролям.

Глобальный поиск охватывает `game.log`. FTS ищет слова в сообщениях, raw-режим ищет
подстроки и может найти строки DEBUG вне индекса. Raw-режим ограничивает один проход
5 000 раундами, 64 МиБ исходного текста, 1 МиБ на строку и ориентиром 8 секунд.
Достижение лимита отображается вместе с неполной выдачей.

При удалении загруженного раунда каталог переносится в скрытый карантин
`.hilleye-deleted` после фиксации удаления в SQLite. Последующий скан завершает
очистку и повторно удаляет исходный каталог, если он появился на прежнем месте.
Резервная копия исключает карантин и каталог раунда, уже отмеченного отсутствующим
при успешном скане.

Импорт сохраняет подготовленные раунды одной операцией переименования каталога.
Каталог и поиск показывают пакет после полной индексации. Временный сбой оставляет
пакет в очереди на повторный скан и отображается в `pending_imports`. Повторная
загрузка идентичных файлов, принятых этим механизмом, возвращает прежние UID.
Разбор multipart идёт после авторизации и ограничивает число полей, объём тела
и время чтения. Точный лимит размера файла применяется отдельно. Параметр
`logs.upload_quota_mb` ограничивает суммарный размер постоянного хранилища
загруженных файлов, включая карантин. Ноль отключает квоту.

Страница растущего `game.log` проверяет индексированный префикс и читает по
смещениям, если необработанный хвост занимает до 8 МиБ. Обычные страницы без
сложных фильтров и контекст показывают свежие строки из этого хвоста. `qdel.log`
выдаёт страницы отдельно для таблицы и сырого текста. Предпросмотр сокращает
длинные строки, полный текст доступен через скачивание.

Версия схемы логов задаётся `PRAGMA user_version`. Для отката на сборку без журнала импортов
остановите все writers и восстановите pre-upgrade копию по процедуре выше. Старая
сборка не понимает журнал незавершённых импортов.

### Сроки хранения

`logs.upload_retention_days`, `logs.audit_retention_days`, `logs.job_retention_days` и `maps.retention_days`
задают независимые сроки. Ноль сохраняет записи без ограничения. Команда ниже
показывает число кандидатов, не меняя файлы или БД.

```bash
python -m core.maintenance --config /opt/Hilleye/config.json prune-logs
```

После проверки кандидатов запустите ту же команду с `--apply`. Параметр
`--optimize-index` вместе с `--apply` объединяет сегменты FTS5, занимая слот записи.
Активные задачи, незавершённые импорты и исходные логи дискового сервера остаются
доступны. Настраивайте расписание применения под согласованные сроки хранения.

HTTP 408 означает остановленный regex, 429 — занятые два общих слота тяжёлых пользовательских
операций либо заполненную очередь. У 429 есть `Retry-After`. Отключение regex-клиента и отмена
запроса завершают процесс. Upload/экспорт используют файлы staging; синхронный файловый worker
завершается до освобождения его ресурсов при отмене.

Карты публикуются версиями через атомарную замену manifest. Предыдущие версии сохраняются,
поэтому их можно читать во время сборки. Если в первых 256 строках `game.log` есть
системная строка `Git revision: <hash>` либо `Commit: <hash>`, просмотр использует
схему той ревизии и запрашивает PNG и отсеки по одному идентификатору версии.
При отсутствии совпадения остаются координаты. При неизвестной ревизии текущая схема
явно помечена как ориентир. Полный SHA можно указать в `maps.github_branch`, чтобы
собрать архивную схему из GitHub. Очистка карт сохраняет текущую версию и версии,
на которые ссылаются раунды. Каталог `map_cache` можно резервировать отдельно, если
исторические сборки нельзя повторить.

## Проверки и наблюдаемость

`/health` сохраняет политику tracker readiness, отдельно добавляя состояние логов, размеры
БД/WAL, свободное место на дисках индекса, uploads и карт, время backup и ограниченные
p50/p95 HTTP-выборки по шаблонам маршрутов. Выборки и
event-loop lag относятся к worker, ответившему на запрос. Ошибки Topic сами по себе не
ухудшают статус здорового Hub-цикла. История snapshots хранится 90 дней по умолчанию.

В логах сервиса есть длительность HTTP-запросов, пользовательских операций и фоновых заданий.
Сборка nginx из репозитория пишет путь без query string. `run.py` пишет шаблон маршрута,
статус и время запроса через телеметрию приложения.
Настроить внешние сигналы на отсутствие backup, ошибки источников, рост pending bytes,
устаревший heartbeat, долгие ответы и заполнение диска. Содержимое логов, cookie и OAuth-коды
не использовать как labels метрик.

```bash
uv run --locked python -m pytest -q
uv run --locked python tools/service_smoke.py --verify-unit
sudo .venv/bin/python tools/service_smoke.py --runtime
```

Runtime smoke запускается в Linux с systemd из venv на `/usr/bin/python3`. Он использует
уникальный временный unit и DynamicUser, локальный mock Hub, отдельное состояние, два workers,
проверяет upload/download и фоновую сборку карты. Рабочий `hilleye.service` и его данные не
перезапускаются. CI выполняет тесты Windows/Linux на Python 3.10/3.14 и отдельный service smoke.
